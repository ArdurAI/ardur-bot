# Customization formats and runtime boundaries

Extensions help the local-first user connect local tools through a generated configuration sheet. Developer helps the builder inspect local processes, redacted logs, and configuration changes. Skills help the researcher keep reusable procedures together. Connectors help the operator find connections that need attention. Plugin previews help the team lead review the components added to a space.

## MCPB and DXT

The parser follows the official [MCPB manifest specification](https://github.com/modelcontextprotocol/mcpb/blob/main/MANIFEST.md) and the repository's versioned schemas. It accepts format versions 0.1, 0.2, 0.3, and 0.4 using `manifest_version` or the legacy `dxt_version` key. The supported launch definition is `server.type`, `server.entry_point`, and `server.mcp_config` with `command`, `args`, `env`, and `platform_overrides`. Format 0.4 `uv` bundles must include an explicit `mcp_config`, as required by the published schema. Ardur does not download or provision runtimes.

Required metadata comes from `name`, `version`, `description`, and `author.name`. Display metadata uses `display_name` and `tools`. `compatibility.platforms` restricts installation to `darwin`, `win32`, or `linux`; `compatibility.runtimes` is parsed as runtime requirements. The host must already provide the requested runtime.

`user_config` generates string, number, boolean, file, and directory controls. The parser uses `title`, `description`, `required`, `default`, `multiple`, `sensitive`, `min`, and `max`. Launch interpolation supports the documented `${__dirname}`, `${user_config.KEY}`, `${pathSeparator}`, and supported system-directory variables. Unknown variables fail validation. Array-valued configuration expands only where the specification permits it.

No ZIP dependency was present or added. `zip.ts` uses Node's built-in `zlib.inflateRawSync` and `zlib.crc32`. It verifies central and local headers, paths, CRCs, expansion limits, file counts, and entry types. It rejects traversal, symlinks, special files, encryption, split archives, and ZIP64. Bundle extraction is limited to 64 MiB and 10,000 files; skill and marketplace uploads have a lower 9 MiB limit.

The native installer writes under Electron's application data directory, partitioned by API origin, user, and space. A journal is encrypted through the existing Electron secret-storage boundary, which rejects Linux's plaintext fallback. A sanitized manifest is written with the extracted server files; launch configuration and sensitive defaults stay encrypted. The API stores arguments and environment values through its existing encrypted secret store and returns environment names and redacted arguments only. Uninstall removes the managed registration and its files. Interrupted installs and removals are reconciled from the journal.

Packaged launches use `placement: "host"`. The paired host service retrieves executable configuration from the authenticated, non-browser `GET /api/host-bridge/mcp` endpoint. Worker messages carry explicit `mcp.tools`, `mcp.call`, `mcp.status`, or `mcp.stop` operations with a server ID and revision; they cannot carry a command or environment. Authorization checks ownership, revision, the active run, the current bot assignment, and resource restrictions. Settings requests may inspect or stop owned servers, but cannot invoke tools. Development launches use the existing worker MCP host and its command allowlist. Log buffers retain at most 200 lines and 96,000 serialized bytes, with redaction before persistence or transport.

## Plugins and marketplaces

The parser follows the official [plugin reference](https://code.claude.com/docs/en/plugins-reference) and [marketplace reference](https://code.claude.com/docs/en/plugin-marketplaces). It reads `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json` or a root `marketplace.json`, and `.mcp.json`. A marketplace requires `name`, `owner.name`, and `plugins`; entries require `name` and `source`. Supported sources are relative folders and the documented `github` and `url` Git source objects, including `ref` and `sha`. `strict`, `category`, `tags`, and `metadata.pluginRoot` are handled where applicable.

Plugin components use the documented `skills`, `commands`, `mcpServers`, and `outputStyles` fields plus their default directories. Additional skill directories are additive; explicit command paths replace the default command directory. `${CLAUDE_PLUGIN_ROOT}` resolves against the installed plugin directory for MCP launch configuration. Optional instructions come from output-style Markdown. A root `CLAUDE.md` is not automatically loaded. Hooks, agents, LSP servers, and other executable component types outside this feature's scope produce an explicit unsupported-format error rather than a partial install.

Git acquisition reuses the existing isolated memory Git transport and its remote-host policy. The default allows GitHub HTTPS URLs. It does not run repository hooks, checkout filters, or submodules, and it rejects symlinks. Fetches have a deadline and snapshots have bounded file counts and sizes. Local folder snapshots use the native folder picker. Curated catalogs are shipped JSON; browsing extensions uses only the existing trusted local-server registry. Neither catalog browsing nor startup fetches an arbitrary marketplace.

An install preview enumerates skills, commands, MCP servers, and instructions and binds consent to a snapshot digest. Each preview expires and is scoped to the current user and space. Installation creates disabled components, enables them after all components are durable, and records incomplete operations for cleanup. Sensitive MCP configuration files are sanitized before extraction; the original marketplace snapshot and launch values use encrypted records. An unfinished plugin remains visible with its installation state and can be removed to retry. Listing plugins is read-only, including on mobile.

## Existing skill and settings seams

Desktop skill import uses a folder picker; web import uses a ZIP upload. Both snapshot the folder and commit `SKILL.md` through the existing memory document lifecycle. The Git option is reserved for marketplaces because folder and ZIP imports fit the existing skill workflow without introducing another source configuration.

File skills have no existing per-bot assignment model. They retain the current user-and-space scope. Taught and learned skills retain their existing bot ownership, and enabled state is checked before runtime loading. Learned skills link to the existing learning inbox. Plugin commands become namespaced skill-backed slash entries through the existing composer skill picker. Plugin instructions are loaded with enabled plugin components.

The five page registrations are in `SettingsOverlay.tsx` because `settings-sections.ts` was absent in this checkout. `customize/registrations.tsx` holds deferred page imports and the Desktop app / Customize grouping. Move the five registrations to the settings-shell registry when that stream lands. `connectors.summary` returns `{ needingReconnection }` for the composer's pending-connection badge. The API contracts and mobile views share connector classification. Mobile presents Skills, Connectors, and Plugins as read-only lists.

The additive migration is `20260924070000_customization`. Its SQL is generated from the prior and current Prisma schemas and uses `taught_skills`, `agent_skills`, `mcp_servers`, `customization_marketplaces`, and `plugin_installs`. There are no data-destructive statements or table renames.
